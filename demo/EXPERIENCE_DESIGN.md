# NULLA-LABS experience design contract

Status: implementation brief for the v101.3 candidate. The visual layer is being introduced separately so it can be reverted without rewriting the Three.js scene or scientific modules.

## Product promise

A learner should be able to explore the 118-element periodic table, inspect curated structures, try catalogued chemistry, explore isotope channels, change temperature where a reference profile exists, measure calibrated geometry, and understand what a result does—and does not—say.

The product is an educational scientific visualizer. A convincing rendering must never be confused with experimental observation, validated molecular dynamics, a reactor model, or a prediction that has not been established.

## Audience ladder

Keep the existing Basic / Laboratory / Scientific Data modes. Evolve them as progressive disclosure, not three separate applications:

1. **First encounter / child-friendly:** one idea at a time, plain language, short action, immediate visual feedback, one “why?” explanation, no unexplained symbols.
2. **Explorer / secondary school:** element identity, atomic number, composition, bonds, mixtures versus compounds, phases, and conservation.
3. **Laboratory / university:** formula and atom-count inspection, explicit reaction catalogue, temperature-profile applicability, measurements and units, model assumptions, missing data.
4. **Research / graduate and doctoral:** provenance per value, source edition and access date, assumptions, parameter ranges, uncertainty, validation status, equations, export metadata, known failure modes, and a reproducible case record.

Do not unlock advanced data by hiding uncertainty. Every level uses the same underlying scientific contracts; higher tiers expose more detail.

## Guided tutorial contract

Each mission should have the same stable structure:
- **Goal:** what the learner will discover, in one sentence.
- **Action:** one verb and one visible target.
- **Observation:** what changed in the 3D scene or data panel.
- **Reason:** the concept behind the change, expressed first plainly and then technically.
- **Evidence:** DATA / MODEL / SIMULATION / ILLUSTRATION / HYPOTHESIS classification and provenance where applicable.
- **Check:** an action-verified objective; completion is never awarded just for opening a panel.
- **Next step:** one useful continuation, plus a way to exit and resume.

Prefer a non-blocking coach card, a visible progress rail, a highlighted target, and an explicit “Try it” action. The coach must not cover the only control the learner is required to click. Permit keyboard navigation and screen-reader announcements. Offer skip, replay, resume, and reduced-motion behavior.

## Liquid-glass design language

The visual direction is macOS / iOS-inspired translucent glass, adapted for a dense scientific workbench:
- one restrained dark-glass base; clear edge highlights; layered blur and saturation; soft shadows; consistent corner radii; light, spring-like transitions;
- a system-font stack so the interface remains quick and available offline; monospace only for formulas, isotope notation, coordinates and raw values;
- readable body text, generous spacing, stable focus rings, minimum comfortable touch targets, and mobile-safe areas;
- restrained semantic accents: cyan for interactive/structural highlights, mint for verified actions, amber for caution/incomplete evidence, and warm orange for nuclear-operation controls;
- motion decorates interaction but never carries meaning alone; support reduced motion and reduced transparency;
- avoid a permanent neon glow on every control, microtext, strong hover scaling on dense data, and shadows that obscure element colors.

The v101.3 CSS file is a presentation layer. It must not create, infer, change, or relabel scientific data.

## Scientific trust model

Every number presented as a fact should have units and a traceable source. Every computed result should identify its equation, inputs, assumptions, and validation test. Every non-predictive animation remains marked as an illustration. Unknown information stays N/D; an absent catalogue path remains absent rather than being generated by the interface.

In particular:
- Q-value is not reaction probability or reaction rate.
- A formula/composition record is not automatically a balanced synthesis equation.
- A phase label is only available where the source profile supports it.
- A visual particle is not automatically a physical particle in a calibrated simulation.
- Hashes prove byte integrity, not scientific truth or authorship.

## Graduate / doctoral workspace innovations

Implement as opt-in tools behind the Scientific Data mode:
- **Evidence inspector:** source, version, access date, value, unit, conditions, transformation, validation result, and explicit N/D fields.
- **Equation / conservation view:** show atomic counts, charge where supported, A/Z conservation for nuclear channels, and how each check was computed.
- **Model card:** intended use, excluded uses, assumptions, parameter ranges, calibration, numerical method, timestep/stability limits if applicable, and test coverage.
- **Reproducibility capsule:** scene ID, element/isotope IDs, controls, temperature, units, application version, source manifest hashes, and export settings; include no hidden telemetry.
- **Research export:** CSV/JSON for data and metadata, plus geometry only when calibrated; include coordinate convention and units in every export.
- **Compare mode:** two structures or conditions side-by-side with the differing inputs called out, not only a visually suggestive overlay.
- **Keyboard-first workbench:** element search by name/symbol/atomic number, command palette, accessible focus order, shortcuts documented in UI, and undo/reset with confirmation for destructive scene changes.

None of these should be simulated as completed capabilities until the corresponding code and tests exist.

## Architecture and ecosystem boundaries

- Keep the scientific core pure and deterministic where possible; keep rendering, interaction state and DOM effects at the interface boundary.
- Preserve the existing strangler approach: characterize behavior before extracting code from the large `app.js` façade.
- Use LEGION C08 concepts for cognitive-load control, adaptive typography, visual grouping and glass UI; C04 concepts for rendering/performance review; C02 concepts for verification. Treat these as design inputs, not browser runtime dependencies.
- Follow the ecosystem catalogue's absorption rule: map → adapt → test → promote. Do not copy a subsystem wholesale or give the UI execution authority.
- Use SCRIBA-style release qualification: hashes, explicit test gates, failure visible as NO-GO, and a reviewable change. A candidate stylesheet is not a production promotion.
- Keep the application local-first, with no required cloud, analytics, third-party UI runtime, or silent scientific-data request.

## Acceptance gates

**Visual and interaction**
- Desktop: 1440×900 and 1280×800; touch tablet: 768×1024; phone: 390×844 and 360×800.
- Basic, Laboratory and Scientific Data modes preserve all existing controls and state behavior.
- Text remains legible at 100–200% zoom; focus visible; keyboard path complete; touch targets are comfortable outside the dense periodic grid.
- No overlapping tutorial coach and required target; modal focus returns to its trigger.
- Verify normal, reduced-motion, reduced-transparency and no-backdrop-filter fallback paths.
- No remote font dependency and no console errors.

**Scientific and release**
- Run `node --check demo/app.js`, `node demo/tests/smoke.mjs`, `node demo/tests/release-baseline.mjs`, and `git diff --check`.
- Check network panel for accidental external requests; the scientific catalogue remains local-first.
- Verify chemistry formula/atom counts, A/Z conservation and Q-value contracts remain unchanged.
- Review screenshots/diffs before promotion. Profile frame rate and memory across low / medium / ultra quality before adding shaders or more particles.
- Promote to the public Pages deployment only after CI and manual responsive/visual review pass.
